**`rent-reminders` edge function** (server-side authority, v3 — see below):
- `preview_single` / `send_single` / `preview_bulk` / `send_bulk` actions.
- Recomputes the tenant's balance itself from `payments` on every call — never trusts a client-supplied balance (spec 1.9, 4.5). If balance changed to PAID between dashboard load and send, the send is rejected with `BALANCE_CHANGED` rather than sending a stale reminder.
- Idempotency key support on `communications` (unique per landlord) — a resend with the same key returns the original result instead of duplicating.
- Template rendering with `{{variable}}` substitution; **rejects sending if any variable is unresolved** (spec 1.7's explicit requirement) rather than sending "$undefined" to a tenant.
- Per-channel delivery: `IN_APP` (a DB row, since there's no separate push infra yet), `EMAIL` (real, via Resend), `SMS` (always fails explicitly with `SMS_PROVIDER_UNAVAILABLE` — no provider configured, and this is surfaced honestly rather than faked).
- Bulk send reuses the exact same per-recipient logic as single send (no parallel/duplicated send path) — deliberately, to avoid the two-systems-computing-differently risk the spec warns about repeatedly.
- **Recent-duplicate-send warning (spec 1.16, done this pass)**: `preview_single`/`send_single` check `communication_recipients` for a `RENT_REMINDER` already sent to this lease within the last 60 minutes. `preview_single` surfaces it as `recentReminder: { sentAt, minutesAgo }` (shown as an inline banner in the modal); `send_single` rejects with `RECENT_REMINDER_WARNING` unless the client passes `confirmRecentDuplicate: true` — the app shows an Alert with "Send Again Anyway" / "Cancel" and only retries with that flag on explicit confirmation. `preview_bulk`/`send_bulk` exclude any tenancy with a recent reminder by default, straight into the existing `removed` list with a human-readable reason — reusing the UI that already renders removed entries, no new bulk screen needed. No per-item bulk override yet (the owner can still send that one individually with confirmation) — acceptable per spec's own wording ("exclude by default, with review available").

## A real bug caught by testing before it shipped

`src/lib/rentCollection/balanceState.ts` (the client-side balance/state display logic, mirrored into the edge function) had two genuine bugs caught by its own test suite on the first run, not found by inspection:

1. **Partial payments were never detected as PARTIAL.** This app records a partial payment as two rows — a `'partial'`-status row for what was actually collected, plus a separate `'pending'` row for the remainder (documented in the existing `arrearsEngine.ts`). The first version of this code checked only the *most recent* row's status, which is usually the `'pending'` remainder row, not the `'partial'` one — so it always fell through to a different state and never showed PARTIAL at all. Fixed by detecting "some payment recorded, balance still owing" (`totalPaid > 0 && totalOwing > 0`) instead of relying on one row's status flag.
2. **A future-dated unpaid charge was counted as currently "owing."** A rent charge due next month that's correctly marked `'pending'` (because it isn't due yet) was being added straight into `totalOwing`, which would have shown a tenant as OUTSTANDING/overdue for rent that isn't even due. Fixed by only counting a pending/overdue row's charge toward `totalOwing` if its `due_date` has actually arrived.

Both fixes were applied to the client copy and the edge function (redeployed as v2) together, and verified with **8 passing tests** covering PAID, PARTIAL, OVERDUE, DUE_TODAY, NOT_DUE, and non-rent-classification exclusion.

**Reminder History screen** (`(tabs)/reminder-history/[leaseId].tsx`, done this pass): reachable via a "History" button on every row in the Rent Collection dashboard. Lists every `RENT_REMINDER` sent to that specific lease, newest first, with the actual rendered message text and a status chip per channel (Delivered/Sent/Failed/Skipped, colored), pulling real data straight from `communication_recipients` + `communication_deliveries` — no separate log table needed since the schema already captured this. Shows the failure reason inline when a channel failed.

**`resend-webhook` edge function** (spec 4.10, done this pass — deployed, `verify_jwt: false` since Resend calls it with no user session): verifies Resend's Svix-signed payload itself (HMAC-SHA256 over `svix-id.svix-timestamp.body`, hand-rolled with Web Crypto since no npm Svix SDK is pulled in), then updates the matching `communication_deliveries` row (by `provider_message_id`, now indexed) from `email.delivered`/`email.bounced`/`email.delivery_delayed`/`email.complained` events to real `DELIVERED`/`BOUNCED`/`UNDELIVERABLE`/`FAILED` status. **One manual step outstanding that only Ebin can do**: register this function's URL as a webhook in the Resend dashboard and set the signing secret it issues as `RESEND_WEBHOOK_SECRET` on this Supabase project — until then the function is deployed but inert (it logs and no-ops rather than erroring).

## Module 2 (Property Health, Life History, Assets, Improvements) — done this pass

Filterable by All/Maintenance/Tenancies/Appliances/Improvements.

**Asset Register** (`(tabs)/assets/`): list (active/retired toggle, optionally scoped to one property via the Health screen's "Appliances" card), add form (property/unit picker, category chips matching the spec's suggested list, make/model/install date/cost/vendor/warranty/service interval), and a detail screen with the service schedule, lifetime service cost, a "Record Service" form that also advances `last_service_date` (which drives the generated `next_service_date`), and a non-destructive "Retire" action (spec 2.9 — status flips to `retired`, history stays intact, never deleted).

**Capital Improvements** (`(tabs)/improvements/`): list + inline add form (title, description, dates, cost, contractor) per spec 2.10's field list, minus permit/warranty/photo fields which are deferred until the Document Vault (2B) exists to actually attach files to.

## Module 3 (Precision Messaging & Announcements) — done this pass

**Scope decision**: this app already had a real, working direct-message feature (`messages.tsx` — a threaded 1:1 chat backed by its own `messages` table, polling-refreshed). Spec 3.1 lists Direct Message and Property Announcement as separate types that "should share infrastructure but should not feel identical in the UI" — since direct messaging already existed and works well, this pass built only the genuinely missing piece, **Property Announcements**, rather than rebuilding direct chat on the batch `communications` pipeline and ending up with two competing direct-message systems (which spec 3.11 explicitly warns against). The `announcements` edge function's `send_direct`/`schedule_direct`/`preview_direct` actions exist and work (same code path as property-wide sends) but aren't wired into any screen yet — available if a future pass wants scheduled/templated direct messages through the same pipeline.

**Recipient model** (spec 3.3): this app's schema has exactly one tenant per lease — no co-tenant/adult-occupant/resident-contact concept exists anywhere. "All Residents" is therefore defined as "all tenants on an active lease at the property" and labeled that way to the owner (active leaseholders), rather than implying a broader resident concept the data can't actually support. Vacant units are automatically excluded and shown as a count, not silently dropped.

**`announcements` edge function**: `preview_property`/`send_property` (and the direct-message equivalents, built but not yet surfaced in UI) resolve the real active-leaseholder audience from `leases`/`units`/`tenants`, render each recipient's message individually with `{{greeting}}`/`{{first_name}}`/`{{property_address}}`/`{{unit}}` — `{{greeting}}` resolves to "Hi Sarah," or, when no first name is on file, "Hello," (spec 3.10's explicit requirement — never "Hello undefined,"). Rejects sending if any variable is unresolved, same discipline as Module 1. Delivers per-recipient via the same Email(Resend)/SMS(unavailable)/In-app channel logic as rent reminders.

**Scheduling (spec 3.8) — real, not a stub**: `schedule_property` stores an `audience_rule` (property + channels + message) on a `SCHEDULED` communications row and resolves **no recipients yet** — audience is explicitly RESOLVED AT SEND TIME, per the spec's own recommendation, so a tenant who moves out between scheduling and firing never receives a message meant for whoever occupied the unit when it was scheduled. A new `process-scheduled-communications` edge function does that resolution and delivery, triggered every 5 minutes by a real `pg_cron` + `pg_net` job (migration `messaging_module`, both extensions newly enabled on this project). Concurrent-run safety via an atomic claim (`UPDATE ... WHERE status = 'SCHEDULED'`) before processing each row. **One manual step for Ebin, same category as the Resend webhook secret**: set `CRON_SECRET` as an edge function secret to the exact value embedded in the migration's cron job body (`584e99c15cd6c4ff8441c7e8fa6bf035a871c17f329ae23e2e80229e32249059`) — until then the cron fires every 5 minutes but the function no-ops since the secret isn't set yet.

**Announcements screen** (`(tabs)/announcements.tsx`, reachable via a new "Announcement" button on the owner Messages screen): property picker, 9 starter templates from spec 3.7 (prefill-and-edit, no legal advice encoded), message composer with a live character count and a rough SMS-segment estimate (SMS itself stays unavailable — this is forward-looking so a future SMS provider doesn't silently produce a costly multi-segment message, per spec 3.6), channel toggles, an "Urgent" flag that requires an extra explicit confirmation before sending (spec 3.9) without bypassing any real opt-out/permission system (none exists to bypass), a real recipient-count/per-channel/exclusion-reasons preview before send (spec 3.4) that must be run before Send is enabled, and a Scheduled list with cancel.

**Deliberately not built in this pass**: Communication History on the property page (spec 3.12) — the data (`communications.batch_id` groups a whole announcement's per-recipient rows for exactly this) is ready but no UI reads it yet; Message Audit Log as a dedicated view (spec 3.13) — the underlying data (sender, audience rule, exact content, channel, final recipients) is all captured in `communications`/`communication_recipients`/`audience_rule`, just not surfaced as a report; in-app announcement inbox items distinct from the tenant's direct-message thread (spec 3.11) — `IN_APP` deliveries exist as rows today but tenants have no dedicated announcements inbox screen yet, only the direct-message thread.

## What's NOT built yet (honest gaps, not oversights)

- **SMS channel** — no provider (e.g. Twilio) configured. Every SMS attempt fails explicitly and visibly rather than silently pretending to work. This is a real decision point for Ebin, same category as the "no AI provider" gap from the onboarding build.
- **Background job queue / outbox pattern** (spec Module 4, sections 4.19–4.21) — bulk sends currently run as one synchronous edge-function request looping through recipients, not a true durable job queue with per-recipient retry/dead-letter tracking. Fine at small-portfolio scale; will genuinely need real queue infrastructure (this app has none — no pg_cron-based job table, no worker process) before it's safe at "hundreds of recipients" scale per spec 4.38.
- **Module 4 (Resilience/API-contract layer)** as a systematic pass — the individual pieces it asks for (idempotency keys, server-recomputed authority, explicit rejection states, atomic claims for cron work) exist everywhere they were needed, but there's no dedicated review pass confirming every endpoint meets the spec's full checklist.
